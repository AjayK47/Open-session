Open Session does not store user passwords. Organizers, reviewers, and speakers
all sign in with a short-lived, single-use code delivered to their email address.
Authorization is determined by organization and event roles after sign-in.

## Human sign-in

<Steps>
  <Step title="Request a code">
    ```bash
    curl -X POST https://your-deployment/api/v1/auth/request-code \
      -H "Content-Type: application/json" \
      -d '{"email":"you@example.com"}'
    ```
  </Step>
  <Step title="Verify the code">
    ```bash
    curl -X POST https://your-deployment/api/v1/auth/verify \
      -H "Content-Type: application/json" \
      -c cookies.txt \
      -d '{"email":"you@example.com","code":"123456"}'
    ```

    The response sets a signed, HTTP-only session cookie.
  </Step>
  <Step title="Reuse the session">
    ```bash
    curl https://your-deployment/api/v1/events -b cookies.txt
    ```
  </Step>
</Steps>

<Warning>
  A sign-in code is returned in an API response only when email delivery is off
  and the environment is `development`, or when evaluation mode is explicitly
  enabled. A normal production deployment sends the code only to the inbox.
</Warning>

## Organization and event access

The first authenticated user creates the single organization for the deployment
and becomes its owner. Owners and administrators can invite teammates from
**Organization settings → Team & invitations**.

Invitations are:

- bound to the invited email address;
- valid for 14 days;
- accepted only after passwordless sign-in;
- assigned an organization role of owner, admin, or member.

Event-level roles grant organizer, reviewer, or speaker access to a specific event.

## API keys

Owners and administrators can create a server-to-server key under
**Settings → API**. The secret is shown once.

```bash
curl https://your-deployment/api/v1/events/{event_id}/sessions \
  -H "Authorization: Bearer <your-key>"
```

Keys carry explicit scopes such as `sessions:write` or `agenda:read` and can be
revoked without affecting human sessions.

## Public endpoints

Routes under `/api/v1/public/...` intentionally need neither a session nor an API
key. They power the public CFP and embeddable programme surfaces.
